# 工作原则

## 降低复杂度

- 拒绝在没有明确收益时增加引入更多状态、变量。
- 圈复杂度尽量控制在 7 以下。
- 尽可能保持单一事实来源，避免在多处维护相同信息。

## 保持干净

- 实现功能与需求时，以最小、最简单、清楚、可维护的机制满足真实产品需求。
- 修复问题时，默认采用最小的根因修复；优先删除多余机制，再复用已有状态、所有权和单一事实来源。
- 在任何时候，严格控制技术债务的增长，尽量避免增加状态、重试、缓存、抽象、依赖、通用框架或绕过方案。
- 若需要复杂机制，必须先评估收益。
- 实现应该足够正确、足够简单和易于维护，但不追求理论场景的完美防御。
- 对于状态同步问题，应该评估为了修复而引入的状态、分支、抽象和维护成本是否值得。
- 如果能在可接受的时间内达到最终一致性，并且用户体验并无大碍，则无需追求状态的完全及时同步，实现最终一致即可。
- 不得以低概率或最终一致性为由削弱认证、安全性、完整性、隐私或不可逆丢失防护。

## 验证与测试

- 默认不添加任何测试用例，除非评估有明显收益，或是已确认的回归问题。
- 避免“验证表演”，避免无意义的长程E2E测试、技术账本建立、SHA256检查。使用逻辑进行验证，检查哈希值并不能证明逻辑正确性。

## 命名与注释

- 使用常见、清楚的词语和缩写命名变量、编写注释及解释问题，避免晦涩表达和不通顺的语句。
- 为不自解释的函数、字段和逻辑补充必要注释；注释说明原因、所有权、信任、时序和恢复，不复述显而易见的代码。

## 与人类协作

- 保留属于用户或协作者的暂存、未暂存、未跟踪和索引状态，不覆盖无关工作。
- 未经明确要求，绝不执行 `git add`。
- 已暂存内容是用户的 review baseline；后续修复保持 unstaged。
- 用户要求 commit 时，只提交当前 index 中的内容，不隐含 staging。

### 执行约束

- 用户要求计划时，只调查和制定计划，不修改代码、配置或仓库状态。
- 用户要求实现时，只执行已确认的最小方案，不随意扩大执行范围。
- 将计划、实现、验证、审查、版本控制和发布视为独立阶段；一个阶段的授权不自动授权后续阶段。
